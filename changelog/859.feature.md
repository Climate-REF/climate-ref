Records what each execution cost in wall time, CPU time and peak memory,
so worker sizing can be based on evidence rather than on an OOM kill in a log.

- The measurement is taken around every execution regardless of executor,
  and it is kept for failed runs as well as successful ones.
- `ref executions resources` aggregates it per diagnostic or per provider,
  and recommends a memory allocation and a core count.
- The `cpu/wall` column is the parallelism signal,
  so a diagnostic sitting near 1.0 gains nothing from more cores.
- A row is flagged `OVER` when its p95 peak has outgrown the memory limit recorded at run time,
  which means the current container size is killing it.

Note that a killed process cannot report on itself, so it contributes no measurement.
The heaviest runs are therefore the ones missing, and every recommendation is biased low.
The failure count and the sample-confidence column are shown alongside so that bias stays visible.
