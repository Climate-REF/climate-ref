Fixed `pmp/enso_proc` and `pmp/enso_tel`, neither of which could complete over the full CMIP6
archive: both sampled 0 of 13 successful executions before this change, and 12 of 12 after.

The REF ENSO driver required exactly one file per variable and raised
`NotImplementedError: Multiple paths found ...` otherwise. Three different situations produce more
than one file, and all three reached these diagnostics:

- a model's timeseries published in time slices, such as `ACCESS-CM2` split at 1949/1950;
- the same file registered from two ingest roots, such as `HadISST-1-1` appearing in both the
  obs4REF cache and the ESGF obs4MIPs mirror. This one affects *every* execution of both
  diagnostics, since both use that reference;
- one period registered in two packagings, such as `GPCP-Monthly-3-2` arriving both as a single
  1983-2023 file and as 40 annual files.

The driver now joins the files into one before handing them over. EnsoMetrics cannot read one
variable from several files: `Read_data_mask_area_multifile` looks like it would, but it pairs
each file with a *variable name* to read several distinct datasets, so passing it time slices
makes every metric fail with `'list' object has no attribute 'strip'` while the run still reports
success and produces no metric values.

Files are sorted before joining (CMIP filenames end with their time range), exact duplicates are
dropped by filename so a mirrored copy is used as-is rather than needlessly rewritten, and the
joined result keeps the first record of each timestamp. That last step is what makes overlapping
packagings work: without it the concatenation is non-monotonic in time and xarray refuses to read
it back. A variable that resolves to a single file is still passed straight through.

The duplicate and overlapping registrations are a property of the catalog rather than of PMP: they
come from ingesting two roots whose contents intersect, and affect 8 datasets in the archive used
here. Only this driver is defended against them.
